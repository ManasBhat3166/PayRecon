# Assumptions

## Business
1. **Matching key** is `(transaction_id, transaction_type)`. Both datasets use the platform's transaction ID.
2. **Reporting scope:** platform transactions dated inside the reporting month are reconciled. Others are counted as "out of scope" and ignored.
3. **Cutoff:** defaults to the last day of the reporting month. A settlement dated *on* the cutoff counts as received; one dated after is outstanding. A cutoff later than month-end lets you see how outstanding items cleared.
4. **Timing differences** are legitimate and temporary. They are reported as outstanding, never as missing. Their amount is excluded from the bank total because the cash had not arrived at cutoff.
5. **Missing settlement** means no settlement record exists at all for an in-scope transaction.
6. **Amounts** are positive in the CSVs. In results, refunds are shown negative so that totals are net.
7. **Rounding:** platform amounts may carry sub-paise precision (e.g. tax-inclusive prices, 3 decimals); the bank settles whole paise using ROUND_HALF_UP. The per-record tolerance is 0.01 (inclusive) and is configurable in `config.py`. A record with `0 < abs(diff) <= tolerance` is ROUNDING_DIFFERENCE and counts as matched-within-tolerance. The aggregate is flagged when `abs(sum of exact differences) > tolerance`.
8. **Duplicate settlements:** same key appearing more than once in the bank file. The earliest by settlement date (then file order) is the original. Duplicates are always excluded from totals, whatever their amount.
9. **Orphan refund:** a refund is valid only if its `original_transaction_id` is a valid PAYMENT in the platform file (any date). An orphan refund is never MATCHED, even if the bank settled it; its amounts still appear in totals so the books balance.
10. **Bank-only settlements** (no platform record, dated within the month up to the cutoff) are reported as INVALID_RECORD and counted in the bank total. Bank-only settlements outside that window are ignored.
11. **Invalid rows** (bad date/amount/type/currency, missing fields, duplicate platform IDs) are excluded from all totals and listed as INVALID_RECORD with the reason.
12. **Duplicate platform transaction IDs:** the first row is kept, later rows are rejected.
13. The `status` column is validated as present but not used to filter (every sample row is `COMPLETED`).
14. **Definitions:** *Matched* = MATCHED + ROUNDING_DIFFERENCE. *Unmatched* = in-scope platform rows not matched (includes invalid platform rows). *Total outstanding* = signed platform amount of TIMING_DIFFERENCE rows. *Net reconciliation difference* = platform net total - bank net total. *Unresolved* = net difference minus outstanding timing. *Total financial discrepancy* = sum of absolute row differences over flagged records (duplicates excluded; reported separately).

## Technical
- Python 3.10+; tested on Python 3.12.3, Streamlit 1.67.0, pandas 3.0.6, pytest 9.2.0 (Linux).
- CSVs are read as text (no float conversion). Dates must be strict ISO `YYYY-MM-DD`. Amounts must be finite and > 0; thousands separators are rejected.
- Currency: INR only (`SUPPORTED_CURRENCIES` in config).
- Sample data is generated by `random.Random(seed)`; the committed CSVs are byte-identical to a fresh run (tested). Bank settlement runs Monday-Friday.
- `anomaly_manifest.json` is an answer key for tests only. The engine never reads it.
- Charts convert Decimals to float for display only; no calculation uses floats.
- No data leaves the machine; no network calls, secrets or credentials.

## Known limitations
- Refund amount is not compared with the original payment amount; multiple refunds per payment are not capped.
- A settlement's `original_transaction_id` is not cross-checked against the platform's.
- Single currency, single reporting month per run; no persistence/database.
- Not tested on a native Windows machine (paths use `pathlib`; CSV writing sets explicit newlines).
